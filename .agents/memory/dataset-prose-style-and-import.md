name: Dataset prose style calibration and DB-import status
description: How to calibrate description tone against reference datasets, and why a written dataset JSON file is not automatically live in the app.
---

**Prose style:** when a user pushes back on a dataset's tone as too flowery/narrative, calibrate against `datasets/region/greece/BC2_ancient_greece.json` rather than more recent narrative-style files (e.g. the mesoamerica Teotihuacan file) — Greece's descriptions are tighter and more encyclopedic (~250-400 chars typical), still vivid, but factual rather than prose-heavy. Re-check average description length and phrasing against it before finalizing a new dataset when the user asks for "concise" or references Greece/Wales as the standard.

**Explicit per-event description rule (user-specified, apply to every dataset going forward):**
1. Never restate the date in the opening sentence — the event's own `date` field already carries it (no "In 648," / "By the 8th century BC," openers). Lead straight with the actor + action.
2. One event = one moment/reign/happening, not a span covering multiple distinct later facts. If a description would need to jump to "his son/grandson later did X," split that into its own event with its own accurate date, rather than compressing two dated facts into one entry.
3. Opening sentence formula: name the actor, then their concrete role/action, anchored to a place — e.g. "Itzamnaaj Kʼawiil becomes king of Dos Pilas, ruling the Petexbatún kingdom from its lakeside capital."
4. Follow with a second paragraph (a `\n\n` blank-line break — confirmed rendered as real paragraph spacing by `EventDetailModal.vue`'s `white-space: pre-wrap`) giving specific, named texture: a distinctive practice, a named relative/ally, or the concrete reason the event mattered — not generic filler adjectives.
5. Prefer exact named people/places over vague abstractions.
6. No moralizing or foreshadowing conclusions — never end a description with an editorial "lesson" the source doesn't state (e.g. "a warning... that later kingdoms will ignore at their own peril"). Stop at what happened.
7. Trace the actual causal mechanism from the source instead of compressing it into a vague summary phrase. E.g. not "stripped the forest for construction, plaster and fuel, degrading the soil" but the real chain: stucco requires burning wood to bake limestone into lime → deforestation → soil erosion → nutrient-rich muck in the bajos buried under sterile clay → crop failures → starvation/abandonment. Only include specifics (like a named drought, or a named destination city) when the source actually states them for that event — don't invent one because a similar-sounding collapse elsewhere had it.
8. Prefer several short simple/compound sentences over one dense sentence stacking multiple facts in subordinate/participial clauses. A description should read as a sequence of plain declarative statements (occasionally joined by a single semicolon), not one sentence carrying three facts at once. This rule is about sentence structure, independent of tense (see rule 10 for tense).
9. Never use a dubious/subjective quality assessment ("some of the finest ever found," "most sophisticated," "stunning," "remarkable accuracy," "one of the greatest") to convey why something mattered. Replace it with a concrete, sourced fact about how it was made or what is specifically unique about it — e.g. instead of "among the most massive structures ever built," give the actual height/volume figures; instead of "remarkable accuracy," give the actual numbers being compared (a 584-day canonical cycle vs. the true 583.92-day period) and why a correction was needed.
10. **Tense (superseded, Aug 2026):** use plain past tense ("became," "built," "organized"), not historical present. The user reworked an entire dataset (Maya civilization) into past tense by hand and confirmed it as the new standard — apply past tense to every future dataset and to any future edits of older present-tense ones.
11. **Title style — mixed, chosen by event kind:** for a founding/site-introduction event (a place appearing as a civilization's new center), use a plain descriptive label, often "[Place] — [its role]" (e.g. "Uxmal — the northern center of the Maya," "Lamanai — Mayan Center"). For an event with real action (a battle, a coronation, a revolt, a collapse), use a narrative sentence naming the actor and action (e.g. "Pakal becomes king of Palenque," "The Xiu Revolt Burns Mayapan"). Don't force a dramatic hook onto a static "X exists/was founded" fact.
12. **Voice — vivid, museum-placard register allowed (relaxed from strict encyclopedic):** occasional modern analogies (e.g. comparing a stepped-pyramid rebuild to nested Matryoshka dolls) and brief second-person reader address (e.g. "if you clap at the foot of the pyramid, the echo mimics a quetzal's cry") are acceptable and encouraged for texture, as long as rules 1-9 (concrete facts, no invented specifics, no moralizing) still hold.
13. **Tag richness:** aim for a fuller tag set per event (5-9 tags is normal, not 4-5) covering theme, faction/place, and event kind. Add a blanket culture tag and a blanket region tag (e.g. "Mayan" + "Mesoamerican") to every event in the dataset in addition to its specific tags — confirmed as the intended standard, not redundancy to clean up.
14. **Cross-dataset deduplication:** before adding an event, check whether it's already covered by a sibling regional/civilization dataset that the event more properly belongs to (e.g. an outside power's intervention in another civilization's city belongs in that outside power's own dataset, not the city's). Drop or skip it here rather than duplicating the same historical moment across two dataset files.
15. **Verify a Wikipedia source has real content, not just a 200 status:** some titles that sound perfect for a niche topic (found while writing an Aztec dataset: `Amantecayotl`, `Penacho_de_Moctezuma`, `Chalco_War`) resolve to a 200-status page that is only a sister-project/disambiguation stub with no article body. An HTTP 200 check alone will not catch this. After fetching, confirm the page actually contains substantive prose about the claimed topic before citing it; if it's a stub, drop that specific event/theme or find a different real article rather than forcing the citation. Also double-check an invented-sounding article slug (e.g. a guessed "1520_smallpox_epidemic") actually resolves before finalizing — it may 404 even when the topic is well documented elsewhere (in that case, cite the broader article, e.g. `Fall_of_Tenochtitlan`, that does cover it).

16. **Location for non-place-bound events (user-specified, Aug 2026):** cultural/customs/social-institution events (e.g. a marriage custom, a kinship system, a craft practice) often have no single defensible coordinate. Bind these to the capital of the relevant region/nation/civilization (e.g. Cusco for Inca, Tenochtitlan for Aztec) rather than picking an arbitrary or loosely-associated site. Reserve specific non-capital coordinates for events genuinely tied to a particular place (a battle, a specific temple, a specific city's founding).

**DB import status:** writing a dataset JSON file under `datasets/` does NOT put it in the running app's Postgres database — `event_datasets` table is a separate store, and there is no discovered script/workflow that auto-scans the `datasets/` folder into it. Confirmed by checking the DB directly: e.g. `AD1_teotihuacan_city_state.json` was fully authored and committed but never appeared in `event_datasets`, while `BC1_olmec_culture.json` (same mesoamerica folder) was already imported. Import happens through an admin-only API (`POST /api/events/import`, `POST /api/datasets`) or an admin UI upload step, not automatically after file creation.

**How to apply:** when a user asks you to "build a dataset," the deliverable is the validated JSON file (correct schema, real 200-status Wikipedia sources, matching the calibrated tone) — do not assume it needs to appear on the live map to be "done," and do not try to hand-write SQL inserts to force it into `event_datasets` unless asked, since that would bypass the app's own import/validation path.
